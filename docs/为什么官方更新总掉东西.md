# 为什么 DSH 官方更新总掉东西

> 这不是一次事故，是四层原因叠在一起。每一层都能让"看着没问题"的检查通过。
> 本文件只描述机制，不含任何个人信息。

## 1. 更新会整包替换 app.asar

Electron 应用的更新，本质是拿官方的新 `resources\app.asar` 覆盖旧的那个。
任何对包内文件的本地修改——`client.js` 的按键行为、`llm-pi-ai` 的协议注册——都会被无声抹掉。

**难发现的原因**：补丁脚本通常先看"现在是不是已经打过"。如果判断逻辑写得不干净
（比如只看某个锚点存不存在，不看它是不是自己打的那个版本），就会返回"已是补丁状态，跳过" + 退出码 0。
于是"更新后补丁没了"变成"脚本全程没报过错"。

**应对**：补丁必须在**更新之后**跑一遍，而不是启动前或人工想起时。而且要放在"DSH 已经关闭"之后——见第 3 节。

## 2. 思考档位继承只认内置目录

自定义路由的模型，除非在 profile 里手写 `reasoningEfforts`，否则界面上**没有强度下拉**。
能否自动继承，取决于路由名能不能匹配内置目录的文件名——这条规则不在任何官方文档里，只能翻源码。

后果是：更新后被抹掉的东西里，最容易丢的就是"哪些模型还能选强度"。

## 3. 一处校验失败会连带整段失效

这是最坑的一层。举例：某 Gemini 配置使用了 `google-generative-ai` 协议，
而这个协议的注册依赖第 1 节那个本地补丁。补丁被更新抹掉之后：

- 该值**不再通过配置校验**；
- 结果是**整个 `providers` 段统一校验失败**，模块没进正常注册阶段；
- 于是同配置下**所有套餐一起消失**，只剩那些走独立配置的还在。

界面表现只是"模型列表变短了"。日志里没有报错，因为配置解析那一步本身是"成功"的——它成功地把整段判定为无效。

**教训**：验收要看**实际生效的目录**（UI 模型选择器真正在用的那个），而不是自己再解析一遍配置文本。

## 4. 插件版本闸门是静默的

第三方插件在 `engines.dsh` 里锁死版本范围。新运行时版本超出范围时：

- 插件**直接不加载**；
- 设置页**不提示**"因版本不符被跳过"；
- 豁免列表不继承——每出一个新版本，就要手动往 `compatibility.json` 补一条精确条目。

用户看到的现象是"更新完插件没了"，且不知道为什么。

## 把这四层串起来

一次常规更新触发顺序：

```
官方替换 app.asar
   → 本地补丁全部消失（第 1 层）
   → 依赖补丁的协议值不再通过校验（第 3 层）
   → 整个 providers 段连带失效，套餐集体消失
   → 插件因版本闸门被静默跳过（第 4 层）
   → 更新脚本仍然报绿：它数的是配置文本行数，不是生效状态
```

所以本项目坚持三条：

1. **升级只用官方安装包**，不自造替换逻辑；
2. **不碰模型配置**——没有"重建"，就不会"重建错"；
3. **验收看本地 API 是否真的答话**，而不是某个文件在不在。
